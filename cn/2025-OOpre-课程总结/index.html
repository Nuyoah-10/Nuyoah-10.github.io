迭代作业最终架构设计

七次作业整体架构如下图所示：

整体架构梳理

代码整体大致可分为三块：输入输出处理、核心实体、集中逻辑处理。

输入输出处理部分

  • MainClass ：进入程序，然后进入Work处理
  • Lexer/Parser/AdventurerNode:词法分析和语法分析，解析雇佣关系字符串，生成关系树来构建上下级关系。

核心实体部分

  • Adventurer:冒险者处理，包含属性管理，物品管理，雇佣关系，战斗及治疗行为。

  • 背包系统：
    创建Item接口;
    Equipment和Bottle作为可放入背包的物品实现此接口;
    Equipment进一步细化为Weapon和Armour，其中Weapon又进一步分为MaigicBook和Sword;
    Bottle分为ManaBottle，AtkBottle,HpBottle,DefBottle四个子类
    以上每个子类都通过extends继承父类。

  • 可用物品部分：建立Usable接口，Bottle和Spell实现此接口，Spell又细分为AttackSpell和HealSpell继承Spell。

集中逻辑处理部分

  • Work：接收输入的命令，调用相应方法执行操作。
  • Factory：统一创建物品和技能实例
  • Observer和Observable:观察者模式，实现一对多的上下级关系，用于援助功能。

迭代过程梳理

  • 第二次作业 中建立 Adventurer类 管理冒险者相关行为，Bottle 类管理药水瓶，Equipment 管理装备，同时把输入输出命令处理写于 MainClass 中。
  • 第三次作业 引入大量内容，加入背包，冒险者四种属性，提出Usable,Spell的概念，同时将Bottle分为四种类别。
    建立 Usable接口, Item接口 将Bottle和Spell类按需求实现接口；同时建立四种Bottle继承Bottle类；此外在本次作业中将命令处理单独放置到 Work类，使得 MainClass 保持其简洁性。
  • 第五次作业 进行了装备的细化，并引入了战斗机制和金钱系统。
    在本次作业中建立 Factory 引入 工厂模式，对Bottle,Spell和Equipment实现统一管理，加入 Weapon 和 Armour extends继承细化装备；再建立 MagicBook 和 Sword 继承细化 Weapon。
  • 第六次作业 加入雇佣关系及援助功能。
    主要做出的变化为加入 观察者模式 ，新增 Observer 和 Observable 实现一对多的雇佣关系；另外在 Adventurer 中完成援助相关功能。
  • 第七次作业 处理输出内容。
    新增 Lexer，Parser和AdventurerNode 递归下降解析输入的字符串，并建立雇佣关系树。
    至此，迭代作业彻底完成。

迭代过程中的主要架构调整及考虑:

1.在第三次作业进行了MainClass的重构，把命令处理单独拆分出Work类，在Work类集中进行字符串拆分及后续逻辑的处理，使得MainClass只负责简单的读入数据，保持了主类的简洁清晰性。(Junit覆盖率也得到提升…)

2.创建Bottle及Equipment等物品时，最开始采用switch-case分支来进行创建；但随着后续物品种类越来越多，在第五次作业中新建Factory工厂模式集中统一管理创建功能，使得主逻辑更加清晰简明，增加代码可读性。

使用JUnit心得体会

以前的C语言学习中几乎没接触过自己单独写测试程序来测试代码，只是简单的在程序中print输出或者多测试几组测试样例。效率比较低下，而Junit的合理使用使得测试不再只是摆设。
在前几次作业时，其实会认为Junit是一个负担，好不容易迭代完代码以后还要自己再构造符合覆盖率的测试，又需要很多时间。但是随着迭代代码量的增加，意识到了Junit的一些好处：

  1. 自己构造测试样例时很难测试到所有情况，但是Junit中详细的 覆盖率数据 可以帮我们解决掉这个问题。在所有代码一点点被覆盖掉的同时，对代码可以实现的功能和分支会了解得更加清楚。
  2. 随着迭代代码量的增加，尤其到后期的时候，仅靠简单的输入输出测试运行整个代码，很难直接找出bug在哪里了。但是通过Junit单元测试可以更好地测试到具体模块的功能，使得debug的难度降低了一些。(?大概吧)
  3. 我认为写Junit算是培养一个良好的习惯(?)，之前写代码基本上是写完就扔给评测机，评测机AC就万事大吉，WA就再修改；但是通过自己写Junit测试程序，逐渐意识到要真正 对自己的代码负责 。在真正的项目中，需要对自己的代码做好完整的功能检测功能测试，再进行交付。

反思
虽然意识到有很多优点，但在使用过程中自己依然存在很多不足，有时会只是为了覆盖率而写Junit,无法真正起到检测程序功能的效果，导致最后的强测中依然挂掉了一些数据点。在后面的学习中会逐渐避免此类问题，真正测试自己的代码！

学习OOpre心得体会

关于面向过程到面向对象

简单的对二者区别的理解：

  • 面向过程 像是把完整的一件事情理清步骤，分为一二三四步，每步用一个函数来实现，再按顺序调用函数完成事件。
  • 面向对象 是以具体的“对象”为中心，每个对象有自己的属性和行为。感觉其思想更偏向于功能划分，而非步骤划分。

在实现简单的功能时，面向过程非常方便，只需要按照步骤拆解清楚按顺序写出来即可；但是随着需要实现的功能越来越复杂，比如需要实现一整个工程项目时，面向对象的思想就变得很重要。
面向对象的代码具有 高度模块化和结构化 的特点,其 封装 的思想让代码写起来清晰很多。在写外层架构的时候不用过多思考内部构建的内容，可以有条理的逐块完成代码(感觉有点像CO子电路的构建过程？)
在编写面向过程的代码时，更关心具体的每个步骤如何实现；但是在写面向对象的时候，会思考每个功能构建在哪个对象中，各个对象如何管理等等，在 组织架构 层面思考的时间会多很多。
总之在写功能复杂的代码的时候感觉面向对象会方便很多，有封装可以使代码模块化，有继承等等功能可以实现功能和属性复用，管理起来更方便一些。

关于git

这是第一次尝试使用 git！之前对 git 的了解知之甚少，但是在一次次作业提交中逐渐了解到了一些 git 的基本用法(虽然只是冰山一角)，感觉这种可版本回退的有分支的管理模式非常有用。但是对其依然不太熟练，会多多练习！

关于CheckStyle

在安装CheckStyle插件以前，对代码风格并没有过度在意。尤其是命名方面在大一学C语言的时候经常a,b,c命名，在回看代码的时候需要思索很久才能想起代码的功能。
在强制检查CheckStyle的制度下，我对驼峰命名，空格，换行等等一系列的代码风格要求逐渐清晰。虽然在第一遍自己写代码的时候依然会出现不太规范的问题，但在CheckStyle的提示下修改的过程中在慢慢加深风格记忆。
好的码风不仅看起来舒适，在debug的时候也会更加清晰，会继续加强CheckStyle的自查！

对OOpre课程的简单建议

  • 除了每周的大迭代作业以外，也许可以适当安排一些程序代码语法相关的小题目(偏向于写短代码)，可能可以更好地掌握一些基础语法的基本使用方式 (类似最后一次的Lexer填空，但是内容和形式可以做出调整)
  • 指导书也许可以把知识点和具体题目拆解为两个页面，查看起来更方便快捷。

写在最后，半学期的OOpre虽然课程数量不是很多，但是让我真正从零基础逐渐学习了面向对象的思想。在一次次迭代作业中虽然略显痛苦(尤其是强测挂掉…)，但是一路走来确有收获。
衷心感谢课程组所有老师和助教们的辛勤付出！OO正课再见啦！
