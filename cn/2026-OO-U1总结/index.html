迭代作业最终架构设计

U1最终作业整体架构如下图所示：

整体分为四个层次

    1. 输入预处理层，白色框内容，包括
    • Main : 单纯输入输出，不做任何多余操作
    • Processor : 预处理，处理空白字符，连续正负号问题
    • Calculator : 集中处理自定义函数和递归函数，只负责处理两类 f 函数
    1. 文法词法处理层，灰色框内容：
    • Token : 记录最小语法单位
    • Lexer : 词法分析，将字符串按Token切分存储
    • Parser : 语法分析，严格按照规则建树：表达式——>项——>因子，递归下降只负责建树而不做任何计算相关的处理
    1. 抽象语法树层，黄色框内容
    • Expr : 表达式层
    • Term : 项层
    • Factor ：因子层，设置为一个统一接口
    • 在最后一次终版作业中共有七个类接入Factor接口，蓝色框内为hw1中的数字因子，幂次因子，表达式因子；绿色框内为hw2中新增的exp因子，自定义函数因子和选择表达式因子；蓝色框内为hw3中新增的求导因子（递归函数放入Calculator处理）。
    1. 核心计算层，橙色框内容
    • Monokey : 将所有因子统一成形式相同的单项式
    • Poly : 集中处理所有计算功能任务

整体架构思路如下：

字符串输入 $\xrightarrow{\text{预处理与词法解析}}$ Token 流 $\xrightarrow{\text{语法解析}}$ AST 树状结构 $\xrightarrow{\text{调用 } toPoly()}$ 核心计算层 $\xrightarrow{\text{化简与 } toString()}$ 最终输出

上面的表格是我按OCavg排序所得到的表格，OCavg是平均圈复杂度，一定程度上可以体现出代码逻辑复杂程度。

  • Lexer ：此类负责表达式的词法分析，将输入字符串切分识别为不同Token，由于Token数量众多所以有大量的分支判断与逻辑处理，导致OCAvg最高。但此种处理方式应该是比较合理的。
  • Poly : 此类集中负责计算，职责相对单一。但是涉及到的计算种类比较多，在第三次作业中我甚至把求导的实现也写入了poly中，导致运算逻辑较为复杂，所以WMC最高。我认为在Poly中集中运算是合理的，但是可能也需要注意不要使此类过于复杂。
  • Parser : 采用递归下降进行语法解析，虽然WMC偏高，但是OCavg为2.5，处于中等水平，说明逻辑尚可。

方法复杂度分析

由于方法数过多，挑选了复杂度较高的一部分进行分析

method CogC ev(G) iv(G) v(G)

  • Poly.toString()：CogC最高，代表可能难以理解难以测试。在这里集中处理了输出方式及优化的所有内容，导致复杂度较高，有优化空间。
  • Lexer.process(char)：虽然CogC=1很低，但圈复杂度v(G)=16，说明有极多的分支判断，测试用例数量需求大。在这里集中进行了词法分析，也是合理的。（可能需要花时间进行测试）
  • Poly.easyFactor()：CogC=18、v(G)=9，都偏高，逻辑包含较多嵌套和分支。后续也正是因为这里的嵌套导致被hack 。静态分析还是可以说明一定问题的（）
  • Calculator.process()：CogC=17、iv(G)=9，偏高。在这里集中处理了递归函数，方法逻辑复杂，耦合度也较高，但还在可控范围内。
  • 其余类复杂度较低，符合低耦合的要求。

总结

总之大部分类和方法较为简单，只有少数几个类的一些方法承担了集中的复杂工作。虽然对单个类而言复杂程度升高，但我认为对架构总体而言是好事。少数集中处理的类可以使得其他类维护起来较为轻松，检查问题时也只需要集中精力检查比较复杂的几个类中一些方法的实现方式。

架构设计体验

第一次初始任务

第一次作业最重点的内容是建立起词法分析和语法分析的框架，建立起树形结构：确立了 Lexer ——> Parser ——> AST 的基础框架。
此次作业所有的因子都可以整理成统一的单项式形式，因此建立一个Mono类记录变量x的指数和系数。

第二次迭代

第二次作业加上了指数表达式、函数表达式以及选择表达式。
分别建立对应的类，接上Factor接口；
新增了Calculator类单独处理自定义表达式，使得Main可以单纯只进行输入输出操作;
另外小小地重构了一下，因为exp的加入，单项式的特征不再仅仅是 $x$ 的指数，还包含exp内部的Poly表达式。第一次作业中的Mono难以继续完成记录同类项的任务。
重新建立了Monokey类作为HashMap键值对的key,好像是第一次清晰认识到键值对内的key可以是一个类，有点神奇。Monokey实现了Comparable和equals，因此可以对同类项进行合并。
同时此次作业中指数也突破了Int的限制，更换为了BigInteger

第三次迭代

新增了y变量和递归函数以及求导因子。

  • 对于y变量，Monokey只需要再增加一个y指数即可，得益于第二次的合理架构，需要修改的内容很少。
  • 对于递归函数，同样在Calculator中进行解析。由于不超过5层所以没有进行什么优化。
  • 对于求导因子，新增deriveFactor接入Factor接口。此外，并未选择指导书中对于每个不同形式的因子都写一套求导的方法，而是在Poly内集中写了一个求导方法，因为最终所有形式的内容都会统一成一致形式，因此在Poly中统一写求导方式我认为更简便一些。但缺点是使得Poly类更冗长了一些且可扩展性不高。

自定义场景

目前除了求导以外其余功能的可扩展性还可以。
比如后续如果加入三角函数或者其余类型的Factor，那么只需要新建一个新的因子类来接入Factor接口，Monokey类也可以稍加修改继续沿用。
但是Poly的求导功能则需要重写。
若从可扩展性角度来考虑，那么求导功能还是分别写在不同的factor内会方便一些。

关于bug

分析自己出现的bug

三次作业中强测均未出现正确性问题。
互测过程中在第三次作业中被hack了6次（惨痛…还是6位不同的同学分别hack的…）。但其实是第二次作业的遗留问题只不过没有被hack到：
是优化长度的过程中计算exp中Poly的gcd出现的问题，嵌套过多导致tle。
目前的解决思路是添加了resCache，把每次计算好的结果储存起来，不再进行无脑的无记忆深层递归，目前来看通过了大家的hack数据。

  • 从复杂度度量角度分析
    Poly.easyFactor()：CogC=18、v(G)=9，都偏高，逻辑包含较多嵌套和分支。bug也正是出在嵌套上。

分析自己发现别人程序bug的思路

第一次未成功hack到，第二次hack到了1位同学，第三次hack到了4位同学
（hack能力精进中？）

主要采用了三种方法

  • 搭建评测机：主要是借助AI搭建，根据题目要求生成大量合法数据进行自动化评测。但是问题也很明显，数据过于随机强度很弱，而本人也没有太钻研如何提升数据的强度。因此本次搭建评测机hack并没有取得很好的效果，后续再继续努力争取提高数据的强度。
  • 看同学代码：由于本人对Java的了解也不是很深，理解也不够强。每次写出自己的代码已经很费时间，所以有点难以在短时间内阅读理解其他不同架构同学的代码，甚至从里面发现问题。因此还是会和AI进行大量的交流。
    • AI阅读代码后大规模提出有可能会出现问题的点，我会从一些角度（如复杂嵌套等）主动引导AI加强检测边界情况。
    • 在AI提出问题的地方我会着重看一下是否真的是有问题的点，并构造相应bug。
  • 随机尝试：在cost限制范围内尽可能用很大的数构造多重嵌套以及多种因子、项结合起来的表达式。虽然此种方法看起来极为不可靠，但是我在第二次作业中依靠胡编数据真的成功hack到两位同学…

分析自己的优化

所做的优化

所做的优化并不是特别多，且有的效果不是很好。主要就是正项提前、快速幂、exp提出gcd

  • 快速幂：在Poly.pow(BigInteger zhishu)中，用了快速幂。但是在研讨课才恍然发现本单元作业应该慎用快速幂。因为快速幂会导致出现大量很长的表达式相乘的情况，大量极长的表达式相乘所消耗的时间已经把快速幂升出来的时间反向耗光了。本次作业使用快速幂反而会拖慢运行效率。
  • 提取公因式优化长度：在Monokey.easyString()中，实现了提取最大公约数。本意是想优化长度但反而因为TLE被hack了6次。

优化与运行效率

积累了一些经验。在优化的时候应该非常谨慎，不要为了优化分数不要运行效率。另外优化之后也需要从多方面考虑是否真正做到了优化（比如快速幂）
过度优化不如不优化，还是应该优先保证正确性。在确认是有效优化且不会损害正确性及大幅降低运行效率后才谨慎优化。

大模型相关使用

代码AI使用率

作业中所有代码均为自己手敲。但是思路方面会借助大模型的框架构建。

  • 正确性 ： 类的设计及类间关系为大模型设计（尤其是第二次作业的MonoKey的提出，自己没有意识到可以这么写），大致有30%为大模型提供思路。
  • 性能优化 ：提出gcd的过程为大模型给出，总共大约有40%是大模型提出。

其余使用大模型情况

  • 找bug ：
    • 自己的作业：每次写完作业之后都会先交给大模型粗略检查一遍是否有明显bug再提交
    • 互测同学的代码：也基本会先由大模型大致检测一遍哪里最有可能出现问题，我再详细看一下具体对应部分的代码
  • 评测机搭建：完全由大模型生成，自己只根据效果和大模型进行多轮修改交互
  • 博客作业以及其他部分未使用大模型

评估效果

  • 大模型在根据题目正向生成框架的时候效果非常好，很快就能生成完全符合题目思路的框架而且出错很少。
  • 在写评测机方面，可以非常快速搭建出一个基本符合要求的评测机。但是在文法的合法性上有时会出现问题，偶尔会有一些不合法的数据被生成数来，需要自己手动调整。另外评测机初始数据极弱，基本不具备查出bug的能力。
  • 在检测bug方面，大模型给人的感觉是广撒网。会一次性提出很多可能存在的问题。但是对照代码仔细一看会发现这里写的根本就没有问题，AI提出的只是冗余设计。但是如果你准确告诉大模型bug对应的数据，AI就可以迅速定位bug定位以及告诉你如何修改。
    总之概览全局找bug或者生成bug数据还是需要人工辅助修正。

他人AI生成痕迹

互测中没有发现很明显的AI痕迹（如大量AI注释或者奇怪方法等）
但是会发现有同学的架构非常独特，比如第一次作业互测房中出现了只有一个类的代码，第二次中也有只写了五个类的代码。但也只是架构不同而已，只是很惊叹居然这么少的类就可以解决问题。

本单元心得体会（兼有本人碎碎念）

距离OOpre已经过去了有一段时间，OOpre的知识点很多都被抛之脑后…所以即便第一单元的作业和pre的最后一次作业有相像之处，但是每周还是写得比较痛苦…大体的经验如下：

  • 好的架构的确非常重要，比如这次建立清晰的AST层次是非常必要的。而且好的架构需要考虑后续增添的内容，尽量具有较好的可扩展性，这样才不用一次一次地重构。另外建立统一性也会对代码的简洁程度大有帮助。
  • 对面向对象的思考确实又加深了一些（本学期除了OO还正在上仓颉，同样是面向对象）。这种封装继承多态的思路确实在解决一些复杂问题时很方便。每个类都只需要管理自己的内容。只需要把整体问题分配给不同的对象，每个对象各司其职即可完成任务。而不用处理复杂的交叉关系。
  • 大模型发展确实越来越迅速，虽然在一些方面仍有不足，但是有时候看到大模型可以迅速生成千行的代码，依然会不自主生发疑惑，我现在学习这个的必要性是什么呢？一直在思考中。
    JYP老师多次在课上说过，“我们的课不叫JAVA编程，而是面向对象，我们真正要学习的是面向对象的思想”。这确实是学习的理由之一。
    扯远一点，面向对象的思想其实好像不止在代码中有用。生活中面对的一些事情同样也是面向对象。一个繁杂的事物需要分别指派给不同的人，只有每个人都干好自己的事情才能完成任务。面向对象有时候感觉是一种全局思维（？）
    至于大模型，也许随着学习的深入会逐渐有更深刻的理解，目前就暂且一边学习一边思考吧~

未来方向

  • 或许实验课可以结束以后一两天内知道实验结果吗…? 实验课的内容一般对当周作业非常有帮助，比较想尽快知道写的是否正确。
  • 另外是否有方式可以得知每次比较优秀的思路实现？比如很好奇每次性能分拿满的同学到底是如何实现的…

写在最后

写下此篇博客时正是阳光灿烂春暖花开，窗外的玉兰开得正盛。
这一个月由于对Java和面向对象确实掌握程度不深，每个周末几乎都贡献给了OO，所以JYP老师说“生活不只有眼前的OO”时非常有感触。
总之第一个月终于安然度过，久闻大名的电梯月也终将来临。
希望可以在繁花似锦的季节中有所收获。
